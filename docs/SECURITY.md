# Security model

This document describes what Compass protects, how, and - just as important -
what it does **not** protect against. Read the last section before you trust
it with something you cannot lose.

---

## 1. The threat model in one paragraph

The realistic attacker is someone who has the phone in their hands: a
partner, a family member, a border official, a thief, a boss with a
five-minute window. They can look at the screen, they can try to guess the
PIN, they can try the "hold the needle on a number" gesture, and they might
plug the phone into a computer. They cannot reach the internet through this
app, because the app has no network permission at all. The goal is that
none of these attacks reveal the *content* of the vault, and that the app
looks boring in a screenshot of the screen.

## 2. The layers

### Layer 1 - The app is a dead end without the unlock

| Mechanism | Where | Notes |
|---|---|---|
| Secret bearing | `ui/screen/CompassScreen.kt` | ±5° tolerance, 1.5 s hold, shows a filling arc |
| PIN | `security/PinStore.kt` | 4-8 digits, salted PBKDF2 hash, escalating lock-out |
| Biometric | `security/BiometricGate.kt` | platform `BiometricPrompt` (API 28+) |
| Decoy vault | `ui/screen/PinScreen.kt` | after 10 failures the keypad is replaced by an empty vault |

### Layer 2 - The files are encrypted at rest

* **Algorithm**: AES-256-GCM (`AES/GCM/NoPadding`).
* **Key**: generated by the Android Keystore with
  `KeyGenParameterSpec` - 256 bit, GCM, no padding, and
  `setRandomizedEncryptionRequired(true)`, so the *platform* generates the
  IV, never the app.
* **Key exportability**: the key is created inside the Keystore and is
  non-exportable. `getEncoded()` is not available for it; it cannot be
  written to a file, a log or a backup.
* **Hardware backing**: on devices with a TEE or StrongBox the key is
  additionally protected by the secure hardware. `KeystoreCipher.isHardwareBacked()`
  reports this (via the deprecated `KeyInfo.isInsideSecureHardware`, which
  is the API 23+ way to ask).
* **IV**: 12 bytes (96 bit), fresh for every single encryption, stored in
  front of the ciphertext.
* **Tag**: 128 bit, verified on every read. A modified or truncated file
  fails with `AEADBadTagException` instead of producing garbage.

**On-disk layout** (inside the app's private data directory, which is
sandboxed by the OS):

```
filesDir/vault/<id>.bin     encrypted payload        (IV + ciphertext + tag)
filesDir/vault/<id>.meta    encrypted metadata JSON  (name, size, date, folder)
filesDir/vault/folders.json encrypted folder list
filesDir/.authstate         encrypted PIN hash + lock-out bookkeeping
cacheDir/decrypted/         transient plaintext, wiped after playback
```

### Layer 3 - The PIN is never stored

The PIN is hashed with **PBKDF2-HMAC-SHA256, 250 000 rounds**, a random
16-byte salt per install, and the result is compared in **constant time**
(`MessageDigest.isEqual`). The hash itself is not stored in the clear: the
whole state file is encrypted with the Keystore key, so a forensic dump of
the data directory yields an opaque blob.

### Layer 4 - The screen cannot be photographed

`FLAG_SECURE` is set on the single window in `MainActivity.onCreate()`.
Because there is only one Activity, the flag covers *every* screen:

* the screenshot button does nothing,
* screen recording and screen sharing produce a black frame,
* the recent-apps thumbnail is blank.

### Layer 5 - There is no network

This is the strongest property of the app, and it is structural rather than
promised:

* the manifest does not declare `android.permission.INTERNET`,
* no dependency declares it transitively (there is exactly one dependency:
  `kotlinx-coroutines-core`, which has no permissions at all),
* the compiled DEX contains no `HttpURLConnection`, no `Socket`, no
  `WebView` and no OkHttp class.

You can verify all of this yourself:

```bash
aapt2 dump permissions dist/Compass-0.1.apk
#   uses-permission: name='android.permission.USE_BIOMETRIC'
#   uses-permission: name='android.permission.USE_FINGERPRINT'
#   uses-permission: name='android.permission.VIBRATE'
```

```bash
# scan the dex for networking classes
python3 - <<'PY'
import zipfile
dex = zipfile.ZipFile('dist/Compass-0.1.apk').read('classes.dex')
for needle in (b'Ljava/net/HttpURLConnection;', b'Ljava/net/Socket;',
               b'Lokhttp3/', b'Landroid/webkit/WebView;',
               b'android.permission.INTERNET'):
    print(needle.decode(), needle in dex)
PY
```

### Layer 6 - Nothing leaves the device

* `allowBackup="false"` and `fullBackupContent="false"` plus
  `res/xml/data_extraction_rules.xml`: the encrypted files are not copied
  into cloud backups or device-to-device transfers.
* The only export path is an explicit, confirmed action that writes a
  **plaintext** copy to a location the user picks - and the confirmation
  dialog says so in plain words.

## 3. The import path, step by step

This is the part that is easy to get wrong, so it is worth spelling out.

1. The user picks files with the system picker (Storage Access Framework).
   **No permission is required** - the user grants access to the exact
   documents they chose, for this one operation.
2. `VaultRepository.import()` opens a `ContentResolver` stream and pipes it
   *directly* into `KeystoreCipher.encryptStream()`. The data is read in
   64 KB chunks; a 1 GB video never exists in memory and never exists
   unencrypted on the disk.
3. The ciphertext is written to `<id>.bin.part` and only renamed to
   `<id>.bin` when the import finished. An interrupted import (the user
   leaves the app, the vault locks, the process is killed) leaves **no**
   half file - the partial file is overwritten and deleted.
4. The metadata is written separately, encrypted, to `<id>.meta`.
5. Only then does the app ask the system to delete the **original** copy
   from the gallery: `MediaStore.createDeleteRequest()` (Android 11+). The
   SAF document URI is translated back into a MediaStore URI first, because
   the platform only understands MediaStore URIs.
6. The app reminds the user to **empty the gallery trash** - until that is
   done, the original still exists in the trash bin of the gallery app.

---

## 4. The playback path, step by step

* **Images** are decrypted into a byte array in memory, decoded, and the
  array is overwritten with zeros. No plaintext file is ever created.
* **Videos** need a seekable file, so the payload is decrypted into
  `cacheDir/decrypted/<id>.mp4`. That file is overwritten with random bytes
  and deleted when playback stops, when the viewer is closed, and whenever
  the vault locks.
* The temporary directory is emptied by `VaultRepository.wipeTempFiles()`,
  which is wired into `LockController`'s cleanup hook.

---

## 5. Auto-lock

| Event | Behaviour |
|---|---|
| `onStop()` (home button, recents, screen off) | the visible screen switches to the compass immediately; the auto-lock timer starts |
| The user comes back within the grace period (default 30 s, configurable 0-600 s) | the vault is still open |
| The grace period expires | the vault locks, temporary plaintext is wiped, thumbnails are dropped, the app returns to the compass |
| The process is killed | the Keystore key stays, the files stay encrypted, the app restarts locked |

## 6. What this app does **not** protect against

Being honest about the limits is part of a security design.

* **A rooted device.** On a rooted phone an attacker can read the app's
  private directory and - more importantly - hook into the Keystore or the
  running process. The encrypted files are still only as safe as the key.
  No app can defend against root.
* **A compromised OS or a malicious keyboard.** A keyboard with
  accessibility permissions can read what you type. The PIN screen is
  protected by `FLAG_SECURE`, but a third-party keyboard is a separate app
  with its own window.
* **Physical attacks on the flash.** `SecureWipe` overwrites files with
  random bytes before unlinking them, but on wear-levelled flash the
  controller may have remapped the physical block. The real protection is
  that the data was encrypted in the first place - the ciphertext is
  worthless without the Keystore key.
* **The secret bearing being observed.** If somebody watches you unlock the
  app three times, they know the bearing. Pick a number that is not
  meaningful to a stranger, and remember that the *combination* of bearing
  and device is the secret.
* **A coerced PIN.** The decoy vault helps against a casual inspection. It
  does not help against a determined adversary who knows the decoy exists.
* **Forensic imaging of a running device.** RAM and the Keystore can be
  dumped on a compromised device. Again: no app can fix that.
* **Losing the keystore file.** See the README - the release keystore
  protects your *app*, the Keystore key protects your *files*. Losing the
  release keystore means the app can never be updated; losing the device
  means the files are gone.

## 7. Checklist before you put real files in

- [ ] You have read the section above and accepted the limits.
- [ ] You have a backup of your original files somewhere else (the vault is
      not a backup system - it is a hiding place).
- [ ] Your phone screen lock is on, with a real PIN or biometric.
- [ ] You have enabled the "delete the originals" flow and emptied the
      gallery trash.
- [ ] You have picked a secret bearing that is not obvious.
- [ ] You have tested the app with a throw-away file first.
